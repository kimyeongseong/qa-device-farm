# 설계 노트

왜 이렇게 만들었는지, 그리고 어디까지만 만들었는지에 대한 기록입니다.

## 출발점

QA를 하면서 실기기가 개인 PC에 물려 있는 구조가 계속 걸렸습니다.

- 기기를 쓰려면 그 기기가 꽂힌 자리로 가야 합니다.
- 누가 지금 뭘 만지는지 알 방법이 없어서, 재현 테스트 중에 남이 앱을 지워버리는 일이 생깁니다.
- 자동화 스크립트를 짜도 그 사람 PC에서만 돕니다.

그래서 목표를 하나로 잡았습니다. **기기를 PC에서 떼어내 네트워크 뒤에 놓고, 브라우저든 스크립트든 같은 API로 접근하게 만들기.**

## 구성

두 개의 프로세스가 돕니다.

| 프로세스 | 포트 | 하는 일 |
|---|---|---|
| `server.py` (FastAPI) | 8001 | 기기 목록, 점유, 입력, APK 설치, 매크로, 스크린샷. 대시보드 정적 파일도 여기서 서빙합니다. |
| `ws-scrcpy` (Node) | 8010 | H.264 저지연 화면 미러링. 포트는 `ws-scrcpy.config.json` 한 곳에서 정의합니다. |

미러링을 직접 만들지 않고 ws-scrcpy를 가져다 쓴 이유는, 화면 전송이 이 프로젝트에서 풀려는 문제가 아니었기 때문입니다. 대신 스트림 기본값(720p·7Mbps·60fps)을 팜 운영에 맞게 고정하는 패치만 얹었습니다 (`NOTICE.md` 참고).

`server.py`에도 `/ws/video/{serial}` 경로로 `adb exec-out screenrecord` 기반 스트림이 있습니다 (대시보드의 '간이 미러링'). Node 없이 Python만으로 도는 폴백입니다. 실측하면 전체 해상도로 나오지만 조작 반영까지 약 1.3초가 걸려서, 지켜보는 용도에는 충분하고 즉각 반응이 필요한 조작에는 ws-scrcpy 쪽이 낫습니다. ws-scrcpy가 죽었거나 Node를 못 까는 환경에서 쓰라고 남겨둔 경로입니다.

## 왜 세션이 없나

처음에는 Appium을 얹을까 고민했습니다. 그런데 이 팜에서 필요한 건 "탭 한 번, 스크린샷 한 장"이 대부분인데, 그걸 위해 세션을 열고 닫는 비용이 너무 컸습니다.

그래서 조작 하나 = HTTP 요청 하나로 갔습니다. 서버는 요청 사이에 기기 세션을 붙들지 않습니다. 상태가 정말 필요한 것은 둘뿐입니다 — "지금 누가 이 기기를 쓰는가"(lease)와, 폴링을 감당하기 위한 기기 정보 캐시. 둘 다 아래에서 따로 다룹니다.

## 점유(Lease)

```
POST /api/devices/occupy   {"owner": "ci-smoke", "ttl_seconds": 300}
  → {"serial": "R3CN30ABCDE", "owner": "ci-smoke", "expires_at": ...}
```

세 가지를 의도했습니다.

1. **TTL이 있습니다.** 반납을 못 하고 죽는 경우가 반드시 생깁니다. CI 잡이 타임아웃되거나, 브라우저 탭이 그냥 닫히거나. 만료 시각을 박아두면 아무도 개입하지 않아도 기기가 돌아옵니다.
2. **"아무거나 하나" 요청이 가능합니다.** 파이프라인은 보통 특정 기기가 아니라 그냥 안드로이드 한 대가 필요합니다. `/api/devices/occupy`가 유휴 기기를 골라 시리얼을 돌려줍니다.
3. **강제 범위를 나눴습니다.** 기준은 "되돌릴 수 있는가"입니다.

| 동작 | lease 강제 | 이유 |
|---|---|---|
| WebSocket 실시간 조작 (화면 보며 탭) | ✗ 표시만 | 급히 확인해야 할 때 락에 막히는 게 더 나쁩니다 |
| HTTP 입력 API | ✓ | CI끼리 같은 기기를 밟습니다 |
| 앱 실행/종료/데이터 초기화 | ✓ | `pm clear`는 남의 테스트 회차를 통째로 날립니다 |
| 배치 작업 전부 | ✓ (기기별 skip) | 열 대 중 한 대가 점유 중이라고 나머지를 막을 이유는 없습니다 |

배치는 점유된 기기를 `error`가 아니라 `skipped`로 보고합니다. 실패한 게 아니라 팜이 거절한 거라서, 운영자가 취할 행동이 다릅니다 — 재시도가 아니라 기다리기입니다.

처음에는 메모리에만 뒀는데, 재시작이 하필 가장 곤란한 순간에 일어난다는 걸 깨달았습니다 — 기기를 잡은 CI 잡은 계속 도는데 팜만 그 기기를 유휴로 착각합니다. 지금은 `device_leases.json`에 기록하고 기동 시 되살립니다. 서버가 죽어 있는 동안 만료된 것은 복원하지 않습니다. 여러 호스트로 늘어나면 파일로는 부족하고 공유 저장소가 필요합니다.

## 입력 주입

좌표는 브라우저와 CI 양쪽에서 들어옵니다. 초기 버전은 이랬습니다.

```python
cmd = f'"{adb_path}" -s {serial} shell input tap {x} {y}'
await asyncio.create_subprocess_shell(cmd)
```

`x`가 검증 없이 셸 문자열에 들어갑니다. 네트워크에 열린 서버에서 이건 그대로 원격 명령 실행입니다. 지금은 정수로 파싱한 뒤 argv로 넘깁니다.

```python
x, y = as_int(event.get("x"), "x"), as_int(event.get("y"), "y")
await adb_exec(adb_path, serial, "shell", "input", "tap", str(x), str(y))
```

APK 업로드도 같은 문제가 있었습니다. 파일 이름이 셸 문자열에 그대로 들어가서, `basename` 처리 후 argv로 넘기도록 바꿨습니다.

이벤트 해석은 `dispatch_input()` 한 곳에 모았습니다. WebSocket 조작, 매크로 재생, HTTP 입력 API가 전부 이 함수를 지나갑니다 — 검증을 세 군데에 복사하면 언젠가 한 군데가 빠집니다.

## 매크로를 다른 기기에서 재생하기

원래 매크로는 좌표 배열이 전부였습니다. 1080x2400에서 녹화한 걸 540x1200 기기에 틀면 전부 엉뚱한 곳을 눌렀고, 그래서 기기마다 따로 녹화하고 있었습니다. 배치 재생을 붙이려면 이걸 먼저 풀어야 했습니다.

녹화할 때 화면 크기를 같이 저장하고, 재생할 때 대상 기기 크기와의 비율로 좌표를 스케일합니다.

```json
{ "version": 2,
  "recorded_on": { "serial": "R3CN30ABCDE", "width": 1080, "height": 2400 },
  "events": [ { "type": "tap", "x": 540, "y": 1200, "timestamp": 0.0 } ] }
```

기존 매크로 파일은 그냥 배열입니다. `read_macro()`가 배열을 보면 v1으로 간주하고 해상도 없이 올려서, 예전 파일도 예전과 똑같이(스케일 없이) 재생됩니다. 마이그레이션 스크립트를 돌릴 이유가 없었습니다.

한계는 분명합니다. 비례 스케일이라 화면비가 다르면 어긋나고, 레이아웃이 재배치되는 폴더블·태블릿에서는 맞지 않습니다. 제대로 하려면 좌표가 아니라 UI 요소를 찾아 눌러야 하는데, 그건 이 도구가 아니라 Appium/Espresso의 영역입니다.

## 로그 수집

크래시 로그를 받는 경로가 "기기 뽑아서 `adb logcat > crash.txt`"였습니다. 기기가 늘면 성립하지 않는 방식입니다.

서버가 기기마다 `adb logcat`을 붙들고 `deque(maxlen=20000)`에 흘려넣습니다. 무제한으로 모으면 장시간 세션에서 메모리를 먹으니 고정 크기 링버퍼로 둡니다.

그런데 밤새 돌리면 넘치는 쪽이 **앞부분**이고, 원인은 대개 거기 있습니다. 그래서 `to_file` 옵션으로 같은 줄을 `logs/`에도 흘려보냅니다 — 메모리는 여전히 상한이 있고 전체 기록은 디스크에 남습니다. 파일 쓰기가 실패해도(디스크 가득 등) 핸들만 버리고 캡처는 계속합니다. 로그 수집이 로그 저장 때문에 죽으면 본말전도입니다.

들어오는 줄마다 세 가지 패턴을 봅니다.

| 종류 | 패턴 |
|---|---|
| Java 크래시 | `FATAL EXCEPTION` |
| 네이티브 크래시 | `F/libc`, `Fatal signal N (SIG...)` |
| ANR | `ANR in ` |

걸리면 별도 목록에 쌓아서 `/api/logcat/{serial}`이 로그 본문과 함께 돌려줍니다. CLI의 `logcat tail`은 크래시가 하나라도 있으면 종료 코드 2로 끝나서, 아무도 로그를 안 읽어도 CI 스텝이 빨갛게 됩니다.

## 기기 정보 캐시

대시보드는 2초마다 폴링합니다. 그런데 기기 하나를 adb로 캐묻는 데 실기기 실측 0.8~2.6초가 걸립니다 — props, `wm size`, `ip addr`, `dumpsys battery` 각각이 왕복이라서. 폴링 주기보다 느린 데다 기기 수에 비례해 늘어나니, 팜을 키울 때 제일 먼저 무너지는 지점입니다.

바뀔 수 있는 것만 다시 읽습니다. 모델·해상도·SDK는 기기가 붙어 있는 동안 변하지 않으므로 한 번만, 배터리는 20초, IP는 60초 캐시입니다. 응답이 약 25ms로 떨어졌습니다. 최신값이 필요하면 `?refresh=1`.

기기가 목록에서 사라지면 캐시도 버립니다. 캐시가 무한히 자라지 않고, 다시 꽂았을 때 예전 값이 남지도 않습니다.

## 접근 토큰

기본은 인증 없음입니다. 사내망에 놓고 쓰는 도구라 그게 맞는 기본값이고, `DEVICE_FARM_TOKEN`을 넣으면 켜집니다.

경계를 어디에 둘지가 실제 고민이었습니다. 대시보드 페이지와 정적 파일은 열어둬야 합니다 — 페이지가 떠야 토큰을 물어볼 수 있으니까요. `/api/health`도 열어뒀습니다. 모니터링이 "살아 있나"를 보려고 비밀을 알아야 할 이유는 없습니다. 나머지는 전부 막힙니다.

브라우저가 헤더를 못 붙이는 두 경로가 문제였습니다. WebSocket은 쿼리스트링으로 토큰을 받습니다. 썸네일 `<img>`도 헤더를 못 싣는데, URL에 토큰을 붙이면 2초 폴링마다 접근 로그에 비밀이 남으므로 fetch 후 blob으로 넘깁니다.

구현하면서 스스로 만든 함정이 하나 있었습니다. 공개 경로 목록에 `"/"`를 넣고 `startswith`로 검사했는데, 모든 경로가 `/`로 시작하니 **인증을 켜도 전부 통과**했습니다. 테스트가 잡았고, 지금은 정확 매칭과 접두사 매칭을 분리해 둡니다.

## 스크린샷 직렬화

같은 기기에 스크린샷 요청이 동시에 들어가면 adb가 자주 깨집니다. 대시보드가 여러 기기를 폴링하면 바로 재현됩니다.

기기별 `asyncio.Lock`으로 한 번에 하나만 통과시키고, 캡처 자체는 블로킹이라 스레드 풀에서 돌립니다. 두 번 재시도해도 실패하면 예외를 올리지 않고 `503`을 반환합니다 — 프론트가 조용히 다시 시도하면 되고, 기기 한 대의 실패가 대시보드 전체를 흔들 이유가 없습니다.

## 만들지 않은 것

이 프로젝트가 다루지 않는 범위입니다.

- **iOS.** USB 독점 문제와 캡처 장치 처리가 필요한데, 안드로이드 실기기 공유라는 원래 목적에서 벗어납니다.
- **에이전트 계층.** 호스트 PC 한 대에 물린 기기만 관리합니다. 호스트가 여러 대로 늘어나면 호스트마다 에이전트를 두고 중앙에서 오케스트레이션하는 구조가 필요합니다.
- **자체 드라이버.** `adb shell input`을 그대로 씁니다. 호출당 수백 ms가 들어서 고빈도 조작에는 느립니다. 더 빠르게 하려면 기기 안에 상주 컨트롤러를 올려야 합니다.
- **사용자별 계정.** `DEVICE_FARM_TOKEN`은 공유 비밀 하나입니다. 누가 무엇을 했는지 구분하지 않습니다. 계정·권한이 필요하면 앞단에 인증 프록시를 두는 편이 맞습니다.
- **한글 IME.** `adb shell input text`가 ASCII만 받습니다. 한글·이모지 입력은 기기에 별도 IME를 설치해야 합니다.
